## 2 运行环境与依赖约定

数据分析项目中的结果不一致，通常并非来自算法实现，而来自运行环境与约定：依赖版本不一致导致同一份代码产生不同结果，路径以绝对形式写入脚本导致换机器后无法定位数据，中间产物缺少记录导致无法追溯每一次运行所用的输入。

三项问题对应三项处理方式：以虚拟环境隔离依赖，按功能分组并锁定依赖版本，按数据、源码与产物的分层组织目录并将路径集中在一处解析。以下部分按实际使用顺序展开：先建立隔离的 Python 环境，再安装与锁定依赖，随后约定目录结构与路径解析方式，最后说明可复现配置与环境检查。本节约定的版本与目录结构在后续各篇中沿用。

### 2.1 Python 与虚拟环境

虚拟环境的作用是为项目建立独立的依赖空间，使不同项目的依赖版本互不影响。常用方式有两种：

```bash
# 方式一：标准库 venv（轻量）
python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

# 方式二：conda（科学计算依赖更省心）
conda create -n dataflow python=3.11 -y
conda activate dataflow
```

`venv` 属于标准库，无需额外安装，适用于依赖以纯 Python 包为主的场景；`conda` 可同时管理非 Python 依赖（如底层线性代数库），在安装科学计算包时更省事。两者择一即可，同一环境内不建议混用 `pip` 与 `conda` 安装包。

版本方面，本系列使用 Python 3.10 及以上，代码在 3.11 验证。由于系统级 Python 通常被操作系统或其他软件占用，在其上直接安装依赖容易产生版本冲突或权限问题，因此建议为项目单独建立虚拟环境。

### 2.2 依赖管理

依赖按功能分组，与后续章节对应，按需安装。分组的好处是：仅使用部分功能时无需安装全部依赖，例如只做表格处理的项目不必安装采集与深度学习相关包。

```text
# requirements-core.txt —— 读写/清洗/变换/可视化（第 2–3、6 篇）
pandas>=2.0
numpy>=1.26
pyarrow>=14.0
openpyxl>=3.1
matplotlib>=3.8
seaborn>=0.13

# requirements-crawl.txt —— 采集（第 2 篇）
requests>=2.31
beautifulsoup4>=4.12
lxml>=4.9
selenium>=4.15
webdriver-manager>=4.0
pymysql>=1.1

# requirements-ml.txt —— 统计/建模/实验（第 7–8 篇）
scipy>=1.11
scikit-learn>=1.3
statsmodels>=0.14
lightgbm>=4.0
shap>=0.44

# requirements-nlp.txt —— 文本/时序（第 4–5 篇）
pyyaml>=6.0
jieba>=0.42
sentence-transformers>=2.5
torch>=2.0

# requirements-image.txt —— 数值/图像（第 9 篇）
Pillow>=10.0
opencv-python>=4.8
```

分组文件中的版本号以 `>=` 给出，表示兼容范围；安装完成后需记录实测版本，以便在相同版本组合下复现结果：

```bash
pip install -r requirements-core.txt
pip freeze > requirements.lock.txt     # 锁定实测版本，保证可复现
```

其中 `requirements-core.txt` 与 `requirements-ml.txt` 覆盖表格处理与建模的完整流程；`requirements-nlp.txt` 中包含 `sentence-transformers` 与 `torch`，体积较大，仅在需要句向量的场景安装。

### 2.3 项目目录

目录按数据、源码、脚本与产物分层，各层的用途如下：

```text
project/
├─ config/          配置唯一权威来源（词表/别名/字段规则）
├─ data/
│  ├─ raw/          原始数据（只读，永久不改）
│  ├─ interim/      中间层
│  ├─ processed/    正式产物
│  └─ features/     高维向量等
├─ src/             公共库（一次实现，禁止重复造轮子）
├─ scripts/         入口脚本（按角色/章节分目录）
├─ docs/            文档
└─ outputs/
   ├─ tables/  figures/  models/  logs/  results/
   └─ registries/
```

分层的目的是区分数据的可修改性：`raw/` 存放原始数据且保持只读，所有派生结果写入 `interim/` 或 `processed/`；`src/` 存放可复用的函数，`scripts/` 仅负责编排调用；`config/` 中的配置（词表、别名、字段规则）作为唯一来源，供各脚本读取。

### 2.4 路径管理

路径若以字符串形式散落在各脚本中，换目录或换机器时需逐个修改。为此在项目内集中解析一次根目录，再由各脚本引用：

```python
from pathlib import Path

def resolve_project_root(start: Path | None = None) -> Path:
    base = (start or Path.cwd()).resolve()
    for c in [base, *base.parents]:
        if all((c / d).is_dir() for d in ("data", "scripts")):
            return c
    raise FileNotFoundError("未找到项目根目录（需含 data/ 与 scripts/）")

PROJECT_ROOT  = resolve_project_root()
RAW_DIR       = PROJECT_ROOT / "data" / "raw"
PROCESSED_DIR = PROJECT_ROOT / "data" / "processed"
TABLES_DIR    = PROJECT_ROOT / "outputs" / "tables"
```

`resolve_project_root` 从当前目录逐级向上查找包含 `data/` 与 `scripts/` 的目录，因此无论从项目根目录还是任一子目录启动脚本，均可正确定位；路径定义集中在本文件，修改时只需改动一处。

### 2.5 可复现配置

除环境与目录外，结果的可复现还依赖以下配置：

1. **固定随机种子**：`np.random.default_rng(42)`、`random_state=42`；
2. **原始数据只读**，所有派生写入 `interim/` 或 `processed/`；
3. **数据类型显式声明**（`Int64` / `category`），避免隐式提升；
4. **关键产物附 `meta.json`**：输入 SHA256 + 参数 + 时间戳。

其中 `meta.json` 用于记录产物与输入的对应关系，便于追溯每次运行的输入与参数：

```python
import hashlib, json, time
from pathlib import Path

def sha256_of(path: Path) -> str:
    h = hashlib.sha256()
    with path.open("rb") as f:
        for chunk in iter(lambda: f.read(1 << 20), b""):
            h.update(chunk)
    return h.hexdigest()

def write_meta(path: Path, inputs: list, params: dict):
    path.write_text(json.dumps({
        "inputs": {str(p): sha256_of(p) for p in inputs},
        "params": params, "created_at": time.strftime("%Y-%m-%d %H:%M:%S")
    }, ensure_ascii=False, indent=2), encoding="utf-8")
```

### 2.6 环境验证与工具链

环境配置完成后，可按以下几项检查是否满足运行条件：

| 检查项 | 判定方式 |
| --- | --- |
| 依赖隔离 | 已在项目虚拟环境中运行，未使用系统级 Python |
| 版本可复现 | 存在 `requirements.lock.txt`，且可据此安装 |
| 路径可移植 | 脚本中无绝对路径，路径均取自统一解析结果 |
| 语法可编译 | `python -m compileall src scripts` 通过 |
| 产物可追溯 | 关键产物目录下存在对应的 `meta.json` |

代码风格与语法可通过工具检查：

```bash
pip install ruff black pytest
ruff check .            # 静态检查
black .                 # 统一格式
python -m compileall src scripts   # 语法编译自检
```

开发过程中，Jupyter 适合探索性分析与可视化调试；需要重复运行的流水线逻辑宜实现为 `.py` 脚本，以便调度与版本管理。

## 3 工程组织与全流程复现

### 3.1 项目数据概览

本系列的数据对象为实习招聘平台的岗位信息。原始数据经采集后落库，包含 **172,063** 条观测记录、30 个字段；经岗位身份确认与去重后得到 **17,144** 个唯一岗位实体，其中 **14,883** 个具备可解析的薪资信息，构成建模样本（另有 2,245 个薪资面议、16 个逻辑异常，合计回到 17,144）。后续各篇的统计口径均以此为基础。

### 3.2 从单文件到分层工程

项目初期以单文件脚本与 Notebook 实现，逻辑集中、路径硬编码，改动后需整体重跑，既难以定位问题来源，也难以保证结果一致。主要问题与重构对策如下：

| 原组织方式 | 重构后 |
| --- | --- |
| 逻辑写在单文件 / Notebook | `src` 库统一实现，`scripts` 只负责编排 |
| 路径硬编码 | `project_paths` 提供单一路径来源 |
| 无阶段概念 | Stage 00–12，可指定区间重跑 |
| 无运行校验 | 门禁、指标与回归锚点 |

Notebook 适合探索性分析，需要重复运行的逻辑以 `.py` 脚本实现，便于复现、调度与版本管理；目录分层与路径解析的具体做法见第 2.3、2.4 节。

### 3.3 阶段化流水线（Stage 00–12）

整条链路按功能拆分为编号固定的阶段，每个阶段完成一项处理并产出可审计的中间产物。阶段与所属功能模块的对应关系如下：

| Stage | 职责 | 功能模块 | 对应篇目 |
| --- | --- | --- | --- |
| 00 | 原始数据 MySQL 只读导出（raw 不可变） | 数据采集 | 02 |
| 01 | 源记录标准化与槽位异常修复 | 数据治理 | 03 |
| 02 | 岗位身份确认（ID / URL / 1:1） | 数据治理 | 03 |
| 03 | 观测快照（搜索来源折叠 + 分类关系层） | 数据治理 | 05 |
| 04 | 版本时序（双签名 + 变化事件） | 数据治理 | 05 |
| 05 | 最终岗位实体（核心版本优先 + 原子替换） | 数据治理 | 03 / 05 |
| 06 | 文本语料（四套版本） | 文本处理 | 04 |
| 07 | 技能与文本特征（long-format） | 信息抽取 | 04 |
| 08 | 文本语义时序（双统计范围） | 文本处理 | 04 / 05 |
| 09 | 公司实体识别（保守映射） | 信息抽取 | 04 |
| 10 | 公司简介快照 / 版本 / 语义时序 | 文本处理 | 04 / 05 |
| 11 | 结构化字段清洗与薪资目标 | 特征构建 | 03 |
| 12 | 建模数据集 + 泄漏审计 | 特征构建 | 03 / 08 |

阶段之间由子进程执行器串联，按区间依次运行：

```python
STAGE_SCRIPTS = {0: ('scripts/pipeline/00_export_raw.py', 'Stage 00 ...'), ...}

def run_stage(stage, args, logger):
    script, title = STAGE_SCRIPTS[stage]
    cmd = [sys.executable, str(PROJECT_ROOT / script)]
    return subprocess.run(cmd, cwd=str(PROJECT_ROOT), capture_output=True,
                          text=True, encoding='utf-8').returncode

for stage in range(args.from_stage, args.to_stage + 1):
    if run_stage(stage, args, logger) != 0:
        break        # 阶段失败即停止，后续阶段不执行
```

以子进程而非直接 `import` 调用，目的是隔离各阶段的运行环境与内存，并使单阶段能够独立运行。

### 3.4 运行控制与质量校验

流水线在运行过程中记录两类结果：门禁与指标。门禁用于判断当前阶段是否满足继续执行的条件，指标用于留痕，两者均以 JSON 形式写入 `outputs/logs/`：

```python
gates = quality.GateRegistry('runner')
ok, note = check_structure(logger);       gates.check('PROJECT_STRUCTURE', ok, note)
ok, note = check_shared_modules(logger);  gates.check('SHARED_MODULES', ok, note)
ok, note = run_regression_check(logger);  gates.check('REGRESSION_CHECK', ok, note)
```

其中 `REGRESSION_CHECK` 负责比对回归锚点。锚点是若干关键中间结果的数量或规模，每次运行后与基线比对，用于判断处理逻辑是否发生变化：

| 锚点 | 值 |
| --- | --- |
| raw 规模 | 172,063 × 30 |
| 唯一 `intern_id` | 17,144 |
| 规范化 URL 唯一 | 17,144 |
| ID ↔ URL | 严格 1:1 |
| 最终岗位实体 | 17,144 |
| 建模样本 | 14,883（+2,245 面议 +16 异常 = 17,144） |

锚点比对的用途在于定位问题：若最终建模样本数出现变化，可沿阶段向前逐级核对，确定是哪一层处理改变了数据规模，而不必逐行排查。

### 3.5 全流程复现

在已有 `raw` 数据的机器上，复现全流程的操作如下：

```bash
# 全流程（复用已存在 raw，不访问 MySQL）
python scripts/pipeline/run_data_pipeline.py --reuse-existing-raw

# 指定阶段区间
python scripts/pipeline/run_data_pipeline.py --from-stage 1 --to-stage 11 --reuse-existing-raw

# 单阶段独立运行
python scripts/pipeline/01_localize_raw_columns.py

# 静态自检
python -m compileall src scripts
```

运行前需按 2.2 节的依赖分组安装环境，并以 `requirements.lock.txt` 锁定版本；`raw/` 目录在运行中保持只读，所有派生数据写入 `interim/` 或 `processed/`。

## 4 小结

环境与目录的组织方式决定了结果能否复现。虚拟环境用于隔离依赖，`venv` 与 `conda` 可择一使用；依赖按功能分组并通过 `pip freeze` 锁定实测版本；目录按数据、源码、脚本与产物分层，原始数据保持只读；路径由统一的解析函数提供，避免绝对路径散落在各脚本中。结果的可复现还依赖固定随机种子、显式声明数据类型，以及为关键产物记录输入哈希与参数。上述约定在后续各篇中沿用，并作为各篇流水线的运行基础。
